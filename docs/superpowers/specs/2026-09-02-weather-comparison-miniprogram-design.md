# 天气预报聚合对比应用 — 设计文档

日期:2026-09-02(2026-09-02 更新:前端从微信小程序改为 H5,数据源范围调整为先接入两家)

## 背景与问题

现有天气预报类 App 普遍只对接单一数据源,而不同天气数据服务商的预测准确度在不同时间、不同地点表现不一致(A 家某次准、B 家某次不准,反之亦然)。用户希望有一个应用,能够同时查看多家天气服务商对同一地点的预报,自行对比判断。

## 目标(MVP,方案 A)

- 用户选定一个城市后,并排展示多家天气服务商对该城市的实时天气、逐小时预报、**未来 3 天**逐日预报(免费版下能统一对齐的最大天数,详见下方"数据源"调研结论)
- 和风天气免费版权限更宽松,可额外展示第 4–7 天(乃至更多)预报,作为它独有的"延伸预报",不强求跨数据源对齐
- 不做历史准确率统计(留作二期 / 方案 B),MVP 只做"并排展示,用户自行判断"

## 数据源

**MVP 第一期只接入两家:和风天气、彩云天气。** 心知天气推迟到后续迭代再接入(不是因为技术原因,是产品侧决定先跑通两家验证价值)。以下接口细节已于 2026-09-02 核实官方最新文档(而非凭经验假设),作为后端实现的依据:

| 服务商 | 定位 | 选择原因 | 免费版实际限制(核实结论) | 接入阶段 |
|---|---|---|---|---|
| 和风天气(QWeather) | 主流数值预报,国内外覆盖全 | 免费/付费权限已拉平,数据最完整,文档成熟 | 每月 5 万次免费额度;逐小时最多 168 小时,逐日最多 30 天。**注意**:官方共享域名(`devapi.qweather.com` 等)正在废弃,新注册开发者需在控制台获取专属 API Host(形如 `xxxx.re.qweatherapi.com`) | 第一期 |
| 彩云天气(ColorfulClouds) | 短临降水预报(雷达+卫星) | 最初看中它的"分钟级降雨预报"差异化能力 | **核实后发现:分钟级降水(`/minutely`)大概率不在免费版范围内**,官方免费版功能列表未列出该项,连"按量购买"付费档的功能列表里这一条都被官方注释隐藏,推测是更高级(企业)套餐才有的能力。免费版实际能拿到的是:实时天气 + 未来 24 小时逐小时 + 未来 3 天逐日预报 | 第一期 |
| 心知天气(Seniverse) | 独立数据源 | 与和风天气底层数据源不同,能形成有意义的对比 | 实时天气接口免费版**只返回 3 个字段**(`text`/`code`/`temperature`,无湿度/风速);逐日预报免费版**只有未来 3 天**(15 天需付费);逐小时预报免费版是否开放官方文档未明确列出,需在实现时用真实 Key 实测确认 | **后续迭代** |

**关于彩云天气 minutely 功能的处理**:实施计划里 `CaiyunProvider` 任务会用真实免费 Key 实际调用一次 `/minutely` 接口验证权限(返回空块即代表确实无权限)。若确认没有权限,MVP 阶段该功能不展示,不影响其余数据的对比价值;后续如产品验证成功、需要这个差异化功能,可以评估升级到彩云天气"按量购买"套餐(但据核实其功能列表里同样没有 minutely,需要联系官方确认是否只有企业套餐才有)。

**架构上为心知天气预留扩展点**:后端的 `WeatherProvider` 统一接口和 `WEATHER_PROVIDERS` 依赖注入令牌数组设计,决定了后续接入心知天气只需新增一个 `SeniverseProvider` 实现并注册进数组,不需要改动聚合逻辑、缓存逻辑或前端展示逻辑。

暂不接入:墨迹天气(开放平台偏企业客户,个人开发者准入门槛高,免费额度不确定)、中国天气网/CMA(无面向个人开发者的官方开放 API)。

## 架构

```
H5 前端(Vite + Vue3 + TypeScript + Pinia)
        │  HTTPS 请求
        ▼
NestJS 后端(聚合 + 缓存 + Key 隐藏)
        │  并行请求
        ├──▶ 和风天气 API
        └──▶ 彩云天气 API
```

后端是系统核心:前端不直接接触任何第三方 API Key,统一由 NestJS 后端代理请求、做数据归一化、加缓存后返回给前端。

- **部署形态**:H5 是普通网页应用,不像微信小程序那样有"request 合法域名白名单"机制,浏览器可以直接请求任意 HTTPS 接口(受标准 CORS 规则约束,需要后端开启对应的 CORS 配置)。项目已具备已备案域名和可部署服务器,满足国内公开网站的合规要求
- **数据库**:MVP 阶段不需要持久化存储(无账号体系、无历史数据),缓存使用内存即可
- **前端技术选型**:Vite + Vue 3 + TypeScript + Pinia(前端目录 `frontend/`,已用 Vite 脚手架创建,含 Vue 3、Pinia、vue-router 依赖)
- **后端技术选型**:NestJS(后端目录 `backend/`,尚未初始化项目内容)

## 组件划分

### 后端(NestJS,目录 `backend/`)

- **`ProvidersModule`**:定义统一接口 `WeatherProvider.getForecast(query)`,MVP 第一期两个具体实现:
  - `QWeatherProvider`
  - `CaiyunProvider`

  各实现负责调用对应第三方 API,并将返回结果转换成统一的内部数据格式(两家字段、单位、结构均不同,归一化是关键职责)。后续接入心知天气时,在这里新增 `SeniverseProvider` 即可。

- **`WeatherModule`**:
  - `WeatherController`:暴露统一接口 `GET /weather?lat=&lon=`
  - `WeatherService`:编排并行调用所有 Provider、聚合结果、处理部分失败

- **`CacheModule`**(NestJS 内置 cache-manager):内存缓存,以经纬度(四舍五入)为 key,TTL 30–60 分钟,降低对第三方免费额度的消耗

- **`ConfigModule`**:管理各家的 API Key(环境变量)

- **CORS**:需要显式开启,允许 `frontend/` 部署后的域名跨域请求

### 前端(H5,目录 `frontend/`,Vite + Vue3 + TS + Pinia)

- **城市/位置选择**:H5 场景下浏览器定位需要用户主动触发(`navigator.geolocation.getCurrentPosition`,HTTPS 环境下才可用),同时支持手动搜索城市切换
- **对比展示页**:并排展示各数据源的实时 / 逐小时 / 未来 3 天预报(和风天气可延伸展示更多天)
- **Pinia store**:管理"当前查看城市"、"聚合天气数据"、"各数据源加载/错误状态"等应用状态
- **API 封装层**:封装对后端 `GET /weather` 接口的请求

## 数据流

1. 用户打开页面 → 请求浏览器定位权限 → 获取经纬度(若拒绝权限,则引导进入手动搜索城市)
2. 前端调用后端 `GET /weather?lat=&lon=`
3. 后端先查内存缓存(以经纬度为 key),命中直接返回;未命中则用 `Promise.allSettled` 并行请求各家 API
4. 每家返回结果经各自 Provider 归一化成统一格式,写入缓存后一并返回前端
5. 前端渲染并排对比卡片(实时 / 逐小时 / 未来 3 天,和风天气可延伸展示更多天)

## 错误处理

- 使用 `Promise.allSettled` 而非 `Promise.all`——某一家超时或失败时,后端仍正常返回其余数据源的数据,不因单一数据源故障导致整个请求失败;失败的一栏前端展示"该数据源暂时不可用,请稍后重试"
- 后端加基础限流(`@nestjs/throttler`),防止前端被刷请求导致自身在各家的免费额度被瞬间打满
- 定位权限被拒绝时,前端自动 fallback 到手动选择城市的引导流程,不阻塞使用

## 测试策略

- **后端**:使用 Vitest(不是 NestJS 脚手架默认的 Jest,当前脚手架版本自带的就是 Vitest),针对每个 Provider 的归一化逻辑写单元测试(mock 第三方 HTTP 响应),以及 `WeatherService` 的聚合逻辑测试(覆盖"部分 Provider 失败"场景)
- **前端**:用 Vite 生态的标准测试工具(如 Vitest + Vue Test Utils)覆盖 Pinia store 逻辑和关键组件;定位授权/拒绝、单个数据源失败时的降级展示等交互路径,MVP 阶段以浏览器人工走查为主
